# Write Approval Gate Design

## Context

The Rust port should keep the upstream CLI behavior where the server is writable by default unless launched with `--readonly`. In an agentic workflow, users usually do not want to restart the MCP server or open a second session just to perform a P4 write. The safety boundary should therefore live at write execution time, not at server startup.

The current `confirmation: "PROCEED"` tool input is not a sufficient boundary because the model can provide that value itself. A real approval path must either be initiated by the server through MCP elicitation or, for clients without elicitation support, use a server-generated one-time token that forces a two-step approval workflow.

## Goals

- Keep default read-write server startup behavior.
- Keep `--readonly` as a global kill switch for write tools.
- Require approval before every `modify_*` tool executes a P4 or review HTTP write.
- Prefer MCP elicitation when the client supports it.
- Provide a soft fallback for clients without elicitation support.
- Remove `confirmation` fields from tool schemas.
- Add `approval_token` as the only fallback approval input.
- Show a compact user-facing summary and command/request preview before approval.
- Exclude secrets from approval summaries, digests, and token responses.

## Non-Goals

- Do not change `query_*` behavior.
- Do not change `--readonly` default semantics.
- Do not add a separate `approve_write` tool.
- Do not introduce long-lived write grants or changelist-wide grants in this change.
- Do not rely on tool annotations as the enforcement boundary.

## Approval Model

Every `modify_*` handler follows the same order:

1. Check `SafetyPolicy` for readonly and toolset restrictions.
2. Build or derive an approval preview for the requested write.
3. Pass the request through the approval gate.
4. Only after approval succeeds, build and execute the P4 invocation or review HTTP request.

The approval gate has two modes.

### Elicitation Mode

If the client declares MCP elicitation support, the server sends an `elicitation/create` request before executing the write. The elicitation prompt presents:

- short summary
- tool name
- action
- target resources
- relevant changelist, workspace, stream, or review id
- compact command or HTTP method/path preview

The write executes only when the user explicitly selects `PROCEED`. Decline, cancel, dismiss, timeout, invalid response, or transport failure must not execute the write.

### Soft Fallback Mode

If the client does not support elicitation, the first write call without an `approval_token` does not execute. It returns an `approval_required` response containing:

- same approval preview shown in elicitation mode
- stable request digest
- generated `approval_token`
- token TTL in seconds
- instruction that the agent must ask the user for approval and retry the same request with the token

The agent may then ask the user in chat and retry the same tool call with `approval_token`.

The token is valid only when all of these are true:

- it was generated by this server process
- it matches the same tool/action/parameters digest
- it has not expired
- it has not been used before

On success, the token is consumed before the write executes. Token reuse, expired tokens, unknown tokens, or tokens attached to changed parameters are rejected.

## Token Contract

Tokens are one-time, short-lived, and process-local. The initial TTL is 5 minutes unless implementation constraints require a narrower value. Tokens are not persisted across server restarts.

The digest must be computed from a canonical form of the write request after excluding approval-only fields such as `approval_token`. It must not include secrets such as passwords, tickets, authorization headers, or full credential-bearing URLs.

## Tool Schema Changes

All modify parameter models get:

```rust
approval_token: Option<String>
```

All existing `confirmation` fields are removed. No tool accepts `PROCEED` as a direct input field for approval.

The server may keep internal approval enums or structs named around `PROCEED` and `CANCEL`, but those are elicitation response values or server-owned token state, not model-controllable command inputs.

## Preview Format

Approval previews use a common compact shape. The exact text may vary by tool, but every preview should be understandable without reading raw JSON.

Example:

```text
Summary: Open 2 files for edit in changelist 123.
Tool: modify_files
Action: edit
Target: //depot/main/a.rs, //depot/main/b.rs
Changelist: 123
Command: p4 edit -c 123 //depot/main/a.rs //depot/main/b.rs
```

Review HTTP writes use the same structure with HTTP fields:

```text
Summary: Add a vote to review 456.
Tool: modify_reviews
Action: vote
Review: 456
Request: POST /api/v11/reviews/456/vote
```

## Tool Annotations

Tool annotations are added as hints only:

- `query_*`: `read_only_hint = true`
- `modify_*`: `read_only_hint = false`
- destructive modify tools or broadly destructive actions should advertise destructive behavior where the framework supports it

Annotations must not replace server-side approval enforcement.

## Testing Strategy

The change needs regression tests around the security boundary, not just happy-path command mapping.

- `confirmation` fields are absent from modify schemas and code paths.
- every `modify_*` call without approval avoids executor/client writes.
- elicitation accept executes exactly once.
- elicitation cancel, decline, dismiss, timeout, or unsupported fallback does not execute.
- fallback returns `approval_required` with preview, digest, token, and TTL.
- fallback token allows the same request once.
- fallback token cannot be reused.
- fallback token expires.
- fallback token fails when parameters change.
- readonly mode still blocks before approval.
- query tools remain unaffected.

Local verification may use the installed `p4` and `p4d` binaries where an integration test needs real Perforce behavior, but unit tests should keep command execution behind the existing executor/client abstractions.

## PR Review Response

The response to the read-only-default review should explain the intended model:

- default writable startup is intentional for agentic workflows
- `--readonly` remains available for locked-down deployments
- write safety is enforced per call through elicitation or token-based soft fallback
- model-provided `confirmation: "PROCEED"` is removed because it is not a user-authenticated approval boundary
